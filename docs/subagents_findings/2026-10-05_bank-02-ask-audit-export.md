# BANK-02

Keywords: BANK-02, audit export, ask_audit, ledger/verify, actor_kind, deployment identity, DR-0004, formula injection, tables_read, executed_trace, redactions, ReDoS, scrub, ChainVerification, dms-269, dms-267
Main idea: GET /v1/audit/export returns one row per ask (who, question, executed SQL, tables, badge, abstain reason, row count, ledger pointer) as CSV or JSONL, with the ledger/verify result, its scope, the store and the unrecorded-ask count on every row. Nothing recorded asks before, so dms.ask_audit is new and append-only. SQL, tables and row count are what the engine ran, not what the customer was shown. The export shows PII-masked literals, as the customer envelope does. Actor is the deployment and says so. Does not close #269.

## What was already recorded

Nothing. `dms.ledger_ref` holds pointers for `amend.confirm` only. `dms.query_run` is read by `routes/runs.py` and written by nothing. Cortex contract 1.2.0 has append and verify and no read-back of an entry, and the ask envelope is returned and dropped. So no store held an ask's question, SQL, tables or outcome, and the export could not be built from existing records.

## What was added

- `dms.ask_audit` (alembic 0005): SELECT for the app roles, INSERT for steward and admin, no UPDATE and no DELETE grant. RLS by tenant. No hash chain; `cortex_entry_id` is a pointer (hard rule 3).
- `dms_core.control_plane.ask_audit`: the row, a Postgres store and an in-memory store behind one port. This is the catalog family beside `SpaceStorePort`, bound the same way at startup (swap: Postgres or process memory). No sixth port, no new dependency, no config key.
- What ran, not what was shown. The customer envelope drops an abstain's SQL and rows and swaps in a placeholder for a document answer, so the export is not derived from it. `dms_executor.executed_trace` records each statement and its row count where it runs (the engine's own `sql_used` and `rows` before envelope post-processing, and `Executor.submit_sql`). `chat_ask` reads it once after the ask. It is a per-thread side channel, not a key on the envelope, so it never reaches the customer or the scorers. A path that runs SQL locally (bronze sheets, demo) records nothing and the row falls back to the envelope's SQL; a comment-only placeholder is exported as empty. Several statements are kept in order; the row count is the last one's.
- `tables_read` lives in `sql_currency.py`, the one sqlglot module. A name is a CTE reference only where sqlglot scope resolves it to a CTE of an enclosing query, so `WITH sales AS (SELECT * FROM sales) SELECT * FROM sales` reports the base table `sales`. A parse or scope failure takes a FROM/JOIN scan, never an empty list for SQL that names a table.
- `chat_ask` records one row after the outcome, errors included. The ladder after the gate moved to `_answer_ask` unchanged; the gate stays in the route. The MCP ask passes the store through.

## What the export does not prove

- `export_verified` means the Cortex chain verified intact when the file was made, and nothing more. Every row and the `X-Audit-Verify-Scope` header say what it covers. Contract 1.2.0 (`contract/openapi-1.2.0.json`) defines the ledger/verify response as `ChainVerification {ok, broken_at}` and nothing else: no count of entries checked, no end, no entry id, and there is no entry read-back to match a row against. So against Cortex 1.2.0 the scope reads `chain_integrity_only; entries_checked not reported by Cortex contract 1.2.0; rows are not matched to ledger entries` and `ledger_entries_checked` is blank. If an engine does send a count (`checked`, which the contract does not define), the scope drops the "not reported" clause and the count is exported.
- It is false on a break (`broken_at` is exported as `ledger_first_break`) and when the ledger cannot be reached. Against the real contract an intact chain reads `ok` (`export_verified` true): `checked` is None, meaning unknown, never 0, so the count rules do not fire. That has a plain consequence: an empty ledger, or a chain that lost its tail entries, still verifies, and DMS cannot detect that. What is available on the DMS side: ledger append returns `LedgerAppendResponse.seq` (the contract's `LedgerEntry.seq`), and the row records it as `ledger_seq` where DMS appended the entry (the certified, governed-metric and generated paths); a pointer that is a Cortex receipt has no seq. That seq is usable for a tail check only together with a reported count. When a count is reported (status `incomplete`, `export_verified` false) it is: 0 entries checked, fewer entries than the exported rows have pointers, or fewer than the highest `ledger_seq` a row recorded, which catches a cut that removes an entry the export points at even when other entries remain; a Cortex-receipt pointer is covered only by the pointer count, and `checked` counts from seq 0 or 1, so a one-entry tail loss on a 0-based chain can pass. A removed middle entry breaks the hash chain, which verify reports with any shape. An empty export has no row to carry the mark; the response headers carry it.
- A row has a `cortex_entry_id` only where the ask had a ledger entry or a Cortex receipt. That includes an abstain that got one. An abstain, error or demo row without one has an empty pointer, and an `ans_` answer id is a label, not an entry, so it is exported empty.
- The memory store holds asks since process start and is bounded by a byte budget; when it evicts, the evicted ask counts as unrecorded. `store_backend` is on every row and in `X-Audit-Store`.
- A failed audit write does not refuse the ask. A Postgres write has a connect and a statement timeout and, after a connection failure, a short cool-down so a dead audit database costs a few seconds once, not each ask. A timeout is an unrecorded ask. The store counts them; `unrecorded_asks_since_start` is on every row and in `X-Audit-Unrecorded-Asks`. It is per process and resets when the API restarts, so it can only show gaps since the last start. Whether a failed write should refuse the ask instead is a policy call, not made here.
- The recorded question is capped at 10,000 characters and the SQL at 50,000, cut with a visible marker (`...[truncated: original was N chars]`) and `truncated=true`. What the ask accepts is unchanged. The order is scrub, mask, then cut, over the first cap plus 2,000 characters, so a secret that straddles the cut is redacted whole (a secret longer than 2,000 characters straddling it is redacted to the end of that window) and the cut never splits a `[redacted]` or a mask token. The stored SQL is cut; `tables_read` is taken from the whole statement.
- PII: the executed SQL and the question go through the same masker the customer envelope uses (`dms_core.pii`) before they are stored, so the audit export holds no personal data the envelope masks. This is a default, flagged for the user: a later policy change can store raw values under tighter access. The masker finds value patterns (emails, phones, IC numbers, accounts, passports with a cue, addresses, dates of birth with a cue); table and column names are left intact. It does not find a person's name in a SQL literal unless a returned row would have masked it, and DMS does not have those rows when it records. Mask tokens are counted in `redactions` with the secrets removed. Secrets are scrubbed first and the masker second, because masking `ss@db.internal` into a token would otherwise break a `scheme://user:pass/ss@host` match; the URL rule also matches through a mask token for text the masker already handled.
- The actor is `DMS_ACTOR_USER_ID` and `actor_kind` is `deployment`. It is not a person until BANK-01.
- Secret removal is a pattern list, not a guarantee. It runs on a normalised view (NFKC, lookalike letters, zero-width characters, block comments dropped, `%3D`-style escapes and JSON unicode escapes decoded) and replaces on the original text, when the row is written and again when it is exported. It covers URL passwords, `password=` and env-style pairs (`DB_PASSWORD`, `OPENAI_API_KEY`, `PGPASSWORD`), JSON keys at any nesting (including a key written with a unicode escape, and JSON escaped inside a string), `Authorization: Basic`, `Cookie:`, `curl -u`, bearer and provider tokens (including Stripe `sk_`/`rk_`/`pk_` keys and `whsec_` webhook secrets), base64 blobs, private-key bodies, a `.netrc` `password X`, a `.pgpass` line (`host:port:db:user:password`), `kubectl --from-literal=KEY=value`, `mysql -pX` and `-p'x'`, an Azure `AccountKey=` of any length and a SAS `sig=`, and the SQL forms `WITH PASSWORD '...'`, `IDENTIFIED BY '...'`, `PASSWORD('...')` and `SET PASSWORD [FOR user] = 'x'` or `= PASSWORD('x')`. The earlier claim that `SET PASSWORD` was closed was true only of the form without `FOR user`; the `FOR bob = PASSWORD('x')` form leaked and is now a test. Every shape is tested in four places: the question, a SQL string literal, a block comment and a line comment. In SQL, the contents of every quoted literal and comment are read as prose and the rest is left alone: no identifier, number or bare column comparison (`token = t2.token`) is rewritten.
- Secrets this cannot find, by design: a secret whose name sits in one JSON field and whose value in another (`{"name":"password","value":"x"}`), a secret split over two fields (`{"pw_part1":"..","pw_part2":".."}`), and a short value in a field with an innocent name (`{"note":"x"}`). A pattern list cannot tell those from data, and rewriting them would rewrite ordinary text. Anything not named as a secret, with no credential shape and under the blob length, is stored as written. The export is for the auditor; treat it as sensitive.
- What it deliberately does not catch, to avoid rewriting ordinary text: a prose `word: value` needs a token-looking value (eight or more characters, mixed character classes) unless the name is a password and the value is credential-like or three plain words, so `Password: reset required for 12 users` is left alone and a short plain password after a colon (`password: hunter`) is not caught unless it is written `password=hunter`; an `is` form (`my token is x`) needs a token-looking value of at least eight characters, so `Our token is ERC20X1 based` is left alone and a seven-character one is not caught. After an explicit `password =` a plain-word passphrase continues until a stop word, a number or the end of the sentence; a credential-like value continues only through following credential-like words. It cannot recognise an arbitrary string as a secret. `redactions` on each row counts what was replaced or masked, so an auditor can see that text was altered.
- How the scrub is bounded (ReDoS). The scrub runs on every `POST /v1/chat/ask` question and on every executed statement, and Python's `re` holds the GIL while it matches, so one backtracking pattern stalls the whole API process, not one ask. The verify of b426b53 measured `password="` plus 44 backslashes at 7.8 s (x2.6 per two more characters; 54 never returned) and quadratic time on repeated `a://b:` and `/* `. Now: no input longer than 64,000 characters reaches a regex (the rest is dropped and the text says `...[scrub window: N chars dropped]`, never returned unscrubbed); quoted values are read per quote character with possessive quantifiers (`(?:\\.|[^"\\])*+`) so no input has two ways to match; alternations are disjoint; the credential-name finder, the comment, URL-password and `has_sql_statement` scanners are linear Python loops with a hard cap instead of lazy regexes; a name is found by its core word with a bounded look-back, not by a lookbehind; an unquoted value is read in a 512-character window (the tail regex is tried at every credential word, and an unbounded read at each of thousands of them is quadratic) and an accepted one is extended to the end of its run once, and a credential word inside a value already taken is skipped. Measured on the development machine over 53 adversarial families, the whole scrub takes at most 0.11 s on a 12,000-character question and 0.20 s on 52,000 characters of SQL (b426b53: 10 s, and some inputs did not return). `tests/test_bank_02_scrub_redos.py` fuzzes the whole scrub and every compiled pattern in the module (found by introspection, so a later pattern is covered) with adversarial input from its own alphabet at 12,000, 52,000 and 1,000,000 characters: absolute ceilings (0.25 s at a window, 4 s at 1 MB, 0.05 s at every size from 12 to 40 characters, which is where exponential time shows first), and a growth check (four times the input must not take eight times as long). The 1 MB runs are in a child process under a deadline, so a pattern that stalls fails the test instead of hanging the suite. It includes the exact `password="` plus backslashes repro. It is a regression gate, not a proof: a regex can still be wrong on an input the fuzzer did not build.
- The append-only guarantee holds for the app roles only. The table owner and a superuser can still UPDATE, DELETE or TRUNCATE, a tenant delete cascades, and compose currently runs the API as `POSTGRES_USER=dms`, a superuser. That is a BANK-04 item; compose is not changed here.
- CSV joins `tables_read` with `;`, which a semicolon-locale spreadsheet may split into columns on import. JSONL carries an array.
- `L2_ANOMALOUS` and demo answers export `badge=validated`; `badge_level` and `ask_mode` tell them apart.

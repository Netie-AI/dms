## What

`DMS_ONTO_GAP_PROPOSE` defaults to 0 and also needs `DMS_ONTO_PG`. Off, `maybe_generative_ask` and `apply_reconfirm` do not import the gap module, so the prompt, the envelope, and the served route stay byte-identical. On, a reconfirm whose reason head is `unknown_measure` or `ungrounded_measure` is appended to a JSONL log after the envelope is built. A daemon thread (or `scripts/onto/propose_gaps.py --since`) drains it. The ask does not call OpenVault.

The model call uses the existing OpenVault client with role `ontology`. DMS does not name a provider or a model. The prompt is the question, the granted catalog (tables, columns, types, declared FKs), and the current measure list. No row samples. The reply is `MeasureGapProposal` or `{"none": reason}`.

Before any human sees it: the name is snake_case, the expression parses as one read, every column is granted, EXPLAIN passes, one run returns a finite number, the name is free, and the normalized expression tree is not already a measure. Failures are dropped with a typed reason. DuckDB error text is not stored. OpenVault HTTP 422 is `gap_propose_unavailable` and the original reconfirm stays.

A valid proposal goes through `store_proposal` (status `proposed`, `served` false, source `onto-gap`). Provenance is the question hash, the ask id, the role stamp, and the validation result. The question text is not stored there. Approval is `scripts/verify/onto_steward.py` `approve-version`. The reconfirm Yes token keeps the original reason and has no SQL, so Yes re-asks. After approval, GROUND-DEFS ranks the measure with the existing embedder or BM25. No keyword map was added.

## Ceiling

ponytail: the gap log is a JSONL file plus a process-local envelope dict. A restart before drain keeps the log and loses the in-memory envelope rewrite. The upgrade is a table keyed by ask id. The HTTP body that already left the process keeps today's reconfirm; the same dict, if still held, is rewritten to `measure_proposed:<name>` when validation passes.

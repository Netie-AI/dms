## What

`DMS_AO_RESPONSE_FORMAT` defaults to off. Only the digit `1` enables it. The flag is read in `build_request_body` and in the string parser, not at import.

Off, the OpenVault ontology body is `role=ontology`, `messages`, and the pydantic class name. `json.dumps` of that body matches the bytes from before this change. A fenced string still raises `JSONDecodeError`, which `complete_structured` records as `ao_model_output_invalid`. Nothing is stored.

On, the body adds `response_format` `{"type":"json_schema","json_schema":{"name": <class>, "schema": <model_json_schema()>}}`. No `strict` key and no model id. `_reject_model_keys` still walks the whole body, including the schema. The six compile classes (`FkAndPkResult`, `ColumnDescriptionResult`, `RawTableTermsResult`, `FkHitSelection`, `SeedSelectionResult`, `SemanticFkJoinDefaultSelection`) do not use a forbidden key. A string that fails `json.loads` is retried once after dropping one leading fence line and one trailing fence of three backticks. The split is `str` methods. A fence that is not the leading line is not searched for. Garbage, including JSON that does not match the class, still records `ao_model_output_invalid`.

DMS does not name a provider or a model. OpenVault still chooses the hop for role `ontology`.

## Ceiling

ponytail: the retry strips one fence and then stops. A reply with prose before the fence, or with two fences, still refuses. The upgrade, if a live compile still fails with the flag on, is whatever OpenVault already returns once `response_format` is set, not a second parser.

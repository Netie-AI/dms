# READY-02

Keywords: READY-02, DMS_SSO, OIDC, Google, Entra, Okta, tenant isolation, service bearer, audit export, dms-634

`DMS_SSO` defaults off. Only the exact digit 1 turns it on. A padded value stays off. Off, the auth middleware is not added and `/v1/auth/*` is not mounted, so spaces, OpenAPI, and the audit export actor basis match the previous API.

On, every GET outside `/health` and the OIDC start and callback paths returns 401 `auth_required`. `POST /v1/auth/login` calls `compliance_gate` before it mints a session. With no Cortex the login is 403 `gate_unavailable`, and the password is not in that body. The CI walk follows included routers, so a new GET that is not on `ALLOWED_GET_PATHS` fails `tests/test_ready02_auth_01.py`. Roles are admin, steward, analyst, and viewer. Analyst may POST `/v1/chat`. Viewer is read-only. `x-dms-*` headers stay a 400 (DR-0004). The login body field is `company`, because a request field named `tenant_id` is forbidden by the actor invariant.

Google, Microsoft Entra, and a generic Okta issuer use an OpenVault `cred_ref`. The authorize URL does not carry the secret. `alg=none` is rejected. One install can hold several companies. A user sees that company's spaces, demo library files, and ask-audit rows. The OpenVault service bearer still reaches the deployment tenant and is not `role_forbidden` on a write.

Ask-audit rows for a verified user use that user id and `actor_kind=person`. Flag off, the actor stays the deployment id.
